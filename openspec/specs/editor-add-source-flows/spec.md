## Requirements
### Requirement: Canonical editor add-source protocol

The system SHALL use `project:addSource` as the default Webview-to-Extension protocol for adding dragged, pasted, selected, generated, or externally referenced sources to editor documents.

#### Scenario: Webview requests a durable source add

- **WHEN** a Webview editor receives a user add-source action for a `.nkv`, `.nkc`, `.nka`, `.nkm`, `.nkp`, or `.nks` document
- **THEN** it MUST send a `project:addSource` message with a `ProjectSourceAddRequest`
- **AND** it MUST include a request id, format id, add kind, destination policy, and available source identity or byte/generation payload metadata
- **AND** it MUST NOT mutate the durable project document before receiving a matching result

#### Scenario: Extension returns a successful source add

- **WHEN** Extension Host resolves the add-source request into a durable source reference
- **THEN** it MUST post `project:sourceAdded` with the matching request id and `ok: true`
- **AND** the result MUST include a durable path, stable source ref, `ResourceRef`, asset/entity id, or allowed remote reference suitable for the target document

#### Scenario: Extension rejects a source add

- **WHEN** Extension Host cannot resolve the add-source request into a durable source reference
- **THEN** it MUST post `project:sourceRejected` or `project:sourceAdded` with `ok: false` and the matching request id
- **AND** the result MUST include machine-readable project-file diagnostics
- **AND** the Webview MUST NOT create clips, nodes, tracks, layers, model refs, or puppet refs from that failed request

### Requirement: Shared Webview add-source client

The system SHALL provide a shared Webview add-source client or hook that handles request lifecycle, browser file projection, optional byte materialization, timeout, cancellation, result matching, and diagnostics for editor add-source flows.

#### Scenario: Browser File is added without durable path

- **WHEN** the Webview only has a browser `File` object and no host-provided durable URI or source path
- **THEN** the shared client MUST submit browser file metadata and bytes only as a create-asset add-source request
- **AND** it MUST NOT infer a durable project path from `File.name`
- **AND** it MUST NOT use `URL.createObjectURL(file)` as project source identity

#### Scenario: Add-source result times out

- **WHEN** no matching `project:sourceAdded` or `project:sourceRejected` response arrives before the configured timeout
- **THEN** the shared client MUST resolve the request as failed with an actionable diagnostic
- **AND** the owning editor MUST leave durable project state unchanged

#### Scenario: Unrelated result is received

- **WHEN** the Webview receives an add-source result with a different request id
- **THEN** the shared client MUST ignore that result for the pending request
- **AND** it MUST keep waiting until the matching request resolves, times out, or is cancelled

### Requirement: Shared Extension Host add-source handling

The system SHALL provide shared Extension Host add-source handling that validates requests, invokes project-file ingest/path policy, returns canonical results, and delegates document mutation to the owning editor's domain adapter.

#### Scenario: Host handles link request

- **WHEN** an add-source request carries a source path or host-authorized source URI for a workspace/project/asset-library/configured-root source
- **THEN** Extension Host MUST run it through the project-file ingest/path policy as a link request
- **AND** it MUST return a portable durable reference before the editor applies any domain add operation

#### Scenario: Host handles byte create-asset request

- **WHEN** an add-source request carries bytes, a paste screenshot, AI/generated bytes, or another byte-only source
- **THEN** Extension Host MUST materialize it through a host-owned create-asset flow
- **AND** it MUST return the resulting durable reference before the editor applies any domain add operation
- **AND** it MUST NOT persist inline large binary payloads in the `nk*` project document

#### Scenario: Host applies domain add after success

- **WHEN** add-source ingest succeeds
- **THEN** the owning editor adapter MUST convert the durable source result into the appropriate domain edit
- **AND** the edit MUST be saved through the editor's ProjectFileStore-backed document lifecycle rather than a package-local file write path

### Requirement: Domain-specific add adapters

The system SHALL keep domain add behavior in each owning editor while sharing only source acquisition and diagnostics.

#### Scenario: Cut adds media

- **WHEN** Cut receives a successful add-source result for media or audio
- **THEN** it MUST add timeline clip data that references the durable source
- **AND** saving and reopening the `.nkv` file MUST recover the added clip without VS Code editor state or cache files

#### Scenario: Canvas adds media

- **WHEN** Canvas receives a successful add-source result for image, video, or audio
- **THEN** it MUST add media node data with durable source fields and separate runtime preview fields
- **AND** saving the `.nkc` file MUST NOT write blob URLs, Webview URIs, thumbnail paths, proxy paths, or runtime preview fields as source identity

#### Scenario: Audio adds media

- **WHEN** Audio receives a successful add-source result for an audio source
- **THEN** it MUST create audio project track/element data that references the durable source
- **AND** saving and reopening the `.nka` file MUST recover the added track without relying on Webview state

#### Scenario: Model adds source

- **WHEN** Model receives a successful add-source result for a supported model source
- **THEN** it MUST update `.nkm` project data through the ProjectFileStore-backed model document path
- **AND** Engine loading MUST use a runtime projection or resolved host path derived from the durable source rather than becoming the save source of truth

#### Scenario: Puppet adds source

- **WHEN** Puppet receives a successful add-source result for a supported puppet source
- **THEN** it MUST update `.nkp` project data through the ProjectFileStore-backed puppet document path
- **AND** runtime bundle loading MUST remain separate from the durable project reference

#### Scenario: Sketch imports source

- **WHEN** Sketch receives a successful add-source result for an image or PSD source
- **THEN** it MAY convert that durable source into editable raster document data
- **AND** the acquisition path MUST still use canonical add-source diagnostics
- **AND** the `.nks` file MUST NOT persist blob, cache, thumbnail, or runtime handles as durable source identity

### Requirement: Legacy add-source bypass cleanup

The system SHALL remove or fail-close old default editor add/drop/import paths that bypass the canonical add-source flow.

#### Scenario: Migrated editor receives legacy add message

- **WHEN** a migrated editor receives a legacy add/drop/import message such as `project:dropImportAudio`, `puppet:dropFile`, `model:dropFile`, `file:dropRequest`, or a private Canvas dropped-file ingest message
- **THEN** the editor MUST reject it, bridge it only through `project:addSource` as a migration-only path, or expose a diagnostic
- **AND** the legacy path MUST NOT silently mutate durable project state

#### Scenario: Migrated Webview handles native file drop

- **WHEN** a migrated Webview receives a native file drop
- **THEN** production add-source code MUST use the shared add-source client
- **AND** it MUST NOT add durable document records from `URL.createObjectURL(file)`, `File.name`, or another runtime-only handle

#### Scenario: Static guard scans migrated code

- **WHEN** boundary or guard tests scan migrated production code
- **THEN** they MUST fail if default add-source behavior still depends on legacy private messages or runtime object URLs for durable source adds

### Requirement: Add-source save and reopen consistency

The system SHALL persist editor-added sources through the unified project-file save lifecycle and recover them after closing and reopening the editor.

#### Scenario: Added source is saved

- **WHEN** a user adds a source through the canonical add-source flow and saves the project file
- **THEN** the file-backed `.nkv`, `.nkc`, `.nka`, `.nkm`, `.nkp`, or `.nks` document MUST write the domain record containing only durable project facts
- **AND** the editor tab MUST be allowed to clear dirty state after the write succeeds

#### Scenario: Saved source is reopened

- **WHEN** the user closes and reopens a saved project file containing an added source
- **THEN** the editor MUST recover the source-backed domain record from the file content
- **AND** it MUST project preview/runtime access from the durable reference without relying on stale Webview memory, VS Code editor state, cache files, or blob URLs

#### Scenario: Open does not save

- **WHEN** a project file is opened or loaded
- **THEN** the editor MUST NOT call save, delete/recreate the project file, or mark the document dirty solely because runtime previews or in-memory baselines are initialized

### Requirement: Unmanaged and runtime source diagnostics

The system SHALL reject unmanaged local paths, runtime handles, and cache artifacts as durable add-source identity with consistent diagnostics and recovery actions.

#### Scenario: Unmanaged local file is added

- **WHEN** a user adds a file from `Downloads`, `Desktop`, a temp directory, or another unmanaged absolute path
- **THEN** the add-source flow MUST reject or pause the add with diagnostics explaining that the file must be moved into the workspace/project, asset library, configured root, or explicit durable asset
- **AND** it MUST NOT persist the absolute path or browser filename as a durable project fact

#### Scenario: Runtime handle is submitted

- **WHEN** an add-source request contains a blob URL, Webview URI, preview URL, Engine token, stream id, range URL, or WebSocket URL as source identity
- **THEN** the add-source flow MUST reject it with a runtime-handle diagnostic
- **AND** the owning editor MUST leave durable project state unchanged

#### Scenario: Cache artifact is submitted

- **WHEN** an add-source request contains a cache, proxy, thumbnail, or legacy cache path as source identity
- **THEN** the add-source flow MUST reject it with a cache-source diagnostic unless an explicit create-asset operation materializes a new durable asset from valid bytes
- **AND** the cache path MUST NOT be saved as project source identity

### Requirement: VS Code Webview runtime validation

The system SHALL validate migrated add-source flows in Extension Development Host using `vscode-extension-debugger` for runtime-sensitive editor behavior.

#### Scenario: Runtime smoke validates add-save-reopen

- **WHEN** Cut, Canvas, or Audio add-source behavior is migrated
- **THEN** validation MUST include a VS Code Webview runtime smoke that adds a source, saves the project, closes or reloads the editor, and verifies the added record remains present
- **AND** a normal browser, Vite dev server, Playwright page, or generic Chrome session MUST NOT be the only acceptance evidence

#### Scenario: Runtime smoke checks dirty state

- **WHEN** a migrated editor opens an existing project file and then saves after an add-source operation
- **THEN** runtime validation MUST verify the tab does not remain permanently dirty after successful save
- **AND** saving MUST NOT close the editor unexpectedly or make the file disappear/reappear as a side effect of load/save coupling
