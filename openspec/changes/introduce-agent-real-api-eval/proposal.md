## Why

Neko Agent can validate single prompts through `neko run` and has a TUI real API suite, but it does not yet have a focused command for real multi-turn AgentSession acceptance: sequential prompts, controller-driven feedback, Skill activation, artifact checks, and model-judge quality review currently require ad hoc scripts or manual TUI use. This gap makes it hard to prove that the actual user-facing Agent path, Skill path, provider/model selection, and generated artifacts remain stable when prompts, Skills, models, or creative workflows change.

## What Changes

- Add `neko eval` as a real-API-only Agent scenario acceptance command under the existing `cli-tui` headless composition root.
- Execute eval cases through a real `AgentSession` in one conversation, using sequential turns rather than TUI queue semantics.
- Support v1 eval modes for `single`, `sequence`, and `feedback-lite`.
- Allow feedback turns to be generated by a real controller model that reads only eval-produced results, not hidden system prompt, AGENTS, Skill source, runtime internals, or logs.
- Add real model judge support for quality review. The judge is the evaluator by default, not the target under test.
- Support command-triggered and natural-language-triggered Skill checks. Natural-language Skill trigger cases require observable Agent-initiated Skill activation.
- Record mandatory result facts in `result.json`: prompts, outputs, generated controller prompts, selected models, Skill activations, artifact/task summaries, judge result, error counters, and failure classification.
- Keep detailed event/log evidence out of v1 output by default. Artifact existence/format checks and task/artifact summaries remain part of the structured result.
- Classify failures with distinct exit codes: pass `0`, case failure `1`, infrastructure failure `2`, and manifest/config invalid `3`.
- Keep `neko run` as the single-prompt headless command. `real-api-suite` may later become an eval preset or wrapper.
- Non-goals:
  - Do not add a mock execution lane to `neko eval`.
  - Do not create a new Agent runtime, scheduler, task system, provider router, Skill trigger mechanism, or business capability.
  - Do not depend on Ink UI components, keyboard input, TUI Zustand UI stores, Webview DOM, VS Code APIs, or Desktop/Electron UI.
  - Do not use eval-only fake tools or direct package-internal business calls to stand in for real Agent behavior.
  - Do not implement complex external controllers, concurrent task orchestration, model matrix runs, Desktop adapters, or VS Code Webview adapters in v1.

## Capabilities

### New Capabilities
- `agent-real-api-eval`: Defines real-API-only Agent scenario evaluation through existing TUI/headless AgentSession runtime, including manifest/result contracts, sequential turns, feedback controller behavior, model judge behavior, Skill activation checks, artifact checks, and failure classification.

### Modified Capabilities
- `quality-validation-release-loop`: Adds `neko eval` evidence expectations for changes that affect AgentSession workflow, Skill activation, provider/model routing, controller/judge behavior, artifact creation, or multi-turn real API acceptance.

## Impact

- Affected packages:
  - `packages/neko-agent/packages/cli-tui`: new `eval` command, manifest parser, AgentSession scenario runner, controller/judge calls, checks, result/report generation, and focused tests for schema/check/report boundaries.
  - `packages/neko-agent/packages/agent`: only if the current AgentSession public API does not expose enough facts to record Skill activations, artifact summaries, task summaries, or selected model identity without reading private storage.
  - `packages/neko-agent/packages/platform`: only if controller/judge model calls need a small existing service reuse path rather than duplicating provider invocation.
- Affected commands:
  - New `neko eval --manifest <path> --output-dir <dir>`.
  - Existing `neko run` remains supported for single-prompt headless execution.
  - Existing `real-api-suite` remains supported during v1 and may later wrap eval.
- Affected artifacts:
  - Eval output directory contains `manifest.json`, `result.json`, and `summary.md` in v1.
  - Detailed event/token/log trace files are deferred.
- Affected validation:
  - `neko eval` is opt-in and requires real provider credentials/network/model availability.
  - Default CI and mock/unit tests remain key-free and must not use `neko eval` as required evidence.
  - Eval parser/check/report logic can have pure unit tests, but Agent behavior acceptance must come from real API eval runs.
